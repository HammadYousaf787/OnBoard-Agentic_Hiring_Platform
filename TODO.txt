STATUS SNAPSHOT
----------------
- Frontend (Next.js) and backend (FastAPI) are now in separate top-level
  folders: frontend/ and backend/.
- Frontend is fully wired to the real backend (auth, jobs, applicants,
  appointments, CV bank) — no more mock/localStorage data.
- Backend: Postgres + MinIO working locally, JWT auth, full CRUD +
  pipeline actions, seed script for demo data, ER diagram + PDF docs.
- Real "AI Job Review" pipeline live: GitHub (PyGithub) + CV/cover letter
  vs. job description, evaluated by Gemini with per-category star scores
  AND written reasoning for each. Triggered per-applicant by HR from the
  applicant detail page. Admin sees an AI usage meter (calls + tokens).
  LinkedIn side is built but inactive — needs a Bright Data API token
  (not yet provided) to actually scrape profiles.
- Applications now come through the platform itself, not Google Forms: a
  separate public app (apply-portal/, port 3001) renders a per-job form from
  the job entry and posts to public backend endpoints (/public/jobs/{id},
  /public/jobs/{id}/apply). The admin/HR platform (port 3000) re-syncs every
  15s so new applicants appear without a reload.


TODO — NEEDED FOR A WELL-FUNCTIONING APP
------------------------------------------

[Backend]
- Public apply endpoint is rate-limited by an in-process, per-IP limiter
  (10/hour) with a honeypot field. It resets on restart, isn't shared
  across workers, and behind a proxy/tunnel every request may look like the
  same IP (X-Forwarded-For is not trusted/parsed). Needs Redis/slowapi and
  a real CAPTCHA (e.g. Turnstile/reCAPTCHA) before public exposure.
- No confirmation email to applicants after they apply, and no
  notification to admin/HR when a new application lands (the platform only
  polls every 15s; nothing pushes/alerts).
- No refresh-token revocation/blacklist. Logout is client-side only
  (tokens just get discarded, not invalidated server-side). Fine for a
  demo, not fine for production.
- No rate limiting / brute-force protection on /auth/login or /auth/signup.
- No password complexity rules beyond min length (8 chars).
- No email verification on signup.
- No "GET /applicants" (all applicants, admin-wide) endpoint — frontend
  currently does N+1 fetches (one per job) and merges client-side. Fine
  at current scale (a handful of jobs), will need fixing if job count
  grows into the hundreds.
- No pagination on any list endpoint (users, jobs, applicants,
  appointments, cv-bank). Same scale caveat as above.
- CV file type/size validation exists only on the public apply endpoint
  (pdf/doc/docx/txt, 10 MB). The authenticated admin/HR upload endpoint
  (POST /jobs/{id}/applicants) still accepts any file of any size.
- No audit log for job/applicant mutations — only user-account
  approvals are audited (approval_events table). Accepting/rejecting an
  applicant, editing a job, etc. leave no history trail.
- JWT_SECRET_KEY in backend/.env is a placeholder dev value — must be
  rotated before any real deployment.
- No automated tests (unit or integration) for the backend.
- No Dockerfile / docker-compose — only runs against locally-installed
  Postgres + MinIO right now.
- No structured logging or error monitoring (e.g. Sentry).
- "Notify me 1 day prior" flag on appointments is stored but does
  nothing — no real reminder is ever sent (email, push, etc.).
- LinkedIn scraping (Bright Data) is wired but inert: BRIGHTDATA_API_TOKEN
  is not set, so every AI Job Review currently scores "linkedin" as
  unavailable (1/5, explicitly explained as missing data, not a real
  score). Needs a Bright Data account + API token from the user.
- Gemini free tier is tight: 5 requests/minute per model, and the
  "gemini-flash-latest" alias (currently gemini-3.8-flash) 503s often. The
  client now retries 4x (honouring 429 retry hints), but "Run AI on all"
  with many applicants can still partly fail — the UI reports "N reviewed,
  M failed" and the failed ones can be re-run. Consider a paid key or a more
  stable GEMINI_MODEL (e.g. gemini-flash-lite-latest answered 3/3 in tests).
- GitHub calls are unauthenticated by default (60 requests/hour limit).
  Set GITHUB_TOKEN in backend/.env (a plain personal access token, no
  scopes needed) before running AI Job Review at any real volume.
- The AI usage meter only tracks Gemini calls (tokens, success/fail).
  GitHub and Bright Data calls aren't logged as usage events even though
  Bright Data's LinkedIn scraper is metered/billed per call — worth
  adding once LinkedIn is actually turned on, so cost is visible too.
- docs/database-schema.html/.pdf (the ER diagram) predates the
  ai_review_details column and ai_usage_events table — needs regenerating
  next time it matters (see backend/docs/render_pdf.py).
- Windows quirk observed repeatedly this session: `netstat`/
  `Get-NetTCPConnection` can report a stale/wrong PID as owning port 8000
  (sometimes a process `Get-Process` can't even find, sometimes a
  different real process than the one actually serving requests) after
  restarting uvicorn a few times. The port always turned out to be
  correctly served despite this — don't trust the reported PID alone;
  confirm by actually hitting an endpoint before killing anything.

[Frontend]
- No "Add Applicant" UI anywhere. Right now applicants only exist via
  the seed script or the public apply portal. If
  admin/HR should be able to manually add a candidate through the UI,
  that screen doesn't exist yet.
- No global toast/notification system — errors are shown inline
  per-component, which works but is inconsistent in placement/timing.
- No pagination/infinite scroll — same scale caveat as backend.
- No password-reset ("forgot password") flow.
- No profile-editing UI for admin/HR to update their own phone/
  country/city after account creation.
- No automated tests (unit or integration) for the frontend.
- No accessibility audit done (keyboard nav, screen readers, contrast).
- Mobile responsiveness has only been eyeballed at a couple of
  breakpoints, not systematically checked.
- No "recent hiring decisions" feed on the admin dashboard — accepting/
  rejecting an applicant currently only shows up on that job/applicant's
  own page, nowhere aggregated for admin visibility. (Raised by user,
  not yet built — see RECOMMENDATIONS.)

[Integration / Infra]
- apply-portal (public, port 3001) and the backend must be reachable from
  the internet for real applicants -- currently localhost only. Needs
  deployment (or a tunnel for demos). Set APPLY_PORTAL_ORIGIN (backend CORS)
  and NEXT_PUBLIC_APPLY_PORTAL_URL (frontend, used for the copy-link card)
  to the real public URLs when that happens.
- Application forms are intentionally standard: every job shares the same
  fields; only title/description come from the job entry, plus an optional
  GitHub field admins switch on per job ("collect_github"). Nothing beyond
  that is configurable per job -- arbitrary admin-defined questions (a form
  builder) aren't built. The GitHub toggle only takes effect on the public
  form; the authenticated add-applicant endpoint ignores it.
- The portal home lists jobs with their full description clamped to 3 lines
  and no search/filter by department or location -- fine for a handful of
  roles, will want filtering/pagination with many.
- After a machine restart nothing auto-starts: Postgres does, but MinIO
  (run from ../minio.windows-amd64...exe with data in C:\minio-data), the
  backend, and both Next apps must be started by hand. MinIO being down
  makes the backend fail at startup with a connection-refused error.
- No environment separation (dev/staging/prod) — one .env, local only.
- No documented deployment process for either half.


RECOMMENDATIONS (non-blocking, worth considering)
----------------------------------------------------
- Add the "recent hiring decisions" feed to the admin dashboard —
  distinct from the existing "Recent decisions" (which is account
  approvals only). Small addition, clear value for admin visibility.
- Containerize both halves (Docker) so a new dev/machine can get running
  without manually installing Python/Node/Postgres/MinIO versions.
- Add a CI pipeline (lint + build + test) before this grows much further
  — right now every check is manual (build + Playwright smoke tests run
  ad hoc during this session).
- Overlap check uses a fixed 60-minute slot for every interview (no per-interview
  duration) and doesn't consider the HR's time zone/working hours.
- HR score isn't yet used anywhere else (job board sort/filter, dashboards).
  The review is free text only; no structured scorecard per interview.
- Video interviews - known gaps: (1) speech-to-text uses the browser's Web
  Speech API, which only works in Chrome/Edge and sends audio to the browser
  vendor's servers - fine for a prototype, replace with a server-side STT
  (or Agora's STT add-on) before real use; (2) recordings are made in the
  interviewer's browser (a canvas + WebAudio mix), so they stop if that tab
  closes and have no duration/seek index (remux with ffmpeg server-side);
  (3) the candidate's link is a bearer secret with no expiry other than the
  interview ending; (4) only one interviewer + one candidate per room; (5)
  Agora tokens use the legacy v1 ("006") format via agora-token-builder - move
  to AccessToken2 ("007") when convenient; (6) the Agora certificate was pasted
  into chat - rotate it in the Agora console before going live; (7) "Live AI"
  costs one Gemini call per ~25s of new speech (free tier: 20 requests/day per
  model!); (8) camera/mic need HTTPS on any non-localhost deployment; (9) the
  candidate's own screen-share works but is not composed specially in the
  recording beyond appearing as their video.
- CV viewer: .doc/.docx can't be previewed in the browser (download only);
  PDFs need a real browser PDF viewer (verified txt inline in headless
  Chromium; PDF preview relies on Chrome's built-in viewer). Presigned URLs
  point at localhost:9000, so a deployed setup needs MinIO_PUBLIC_URL / a
  reverse proxy so browsers can reach it.
- CV bank has no direct upload yet (entries only come from rejected
  applicants). Add "upload a CV to the bank" if it should be a general talent
  pool.
- Coding assessment is only a stage for now: nothing is actually sent to
  the applicant, no test is hosted, and no score/result is recorded. Decide
  how the assessment is delivered (link to a platform? in-app?) and how HR
  records the outcome.
- "Technical" is tied to the same flag as the GitHub form field (per the
  spec that GitHub-required jobs need a coding assessment). Split into two
  flags if a role needs one without the other.
- "Interview Pending" reuses the existing assessment_passed stage, so the
  HR "Pending Scheduling" page still lists exactly those applicants. The
  Interview Pending panel also shows interview_scheduled/accepted applicants
  (with a badge) so nobody vanishes from the job page. Decide whether they
  deserve their own panels once the interview flow is built out.
- Bulk reject has no per-applicant note field (only the CV-bank auto-save
  setting applies); the single-applicant reject dialog still has one.
- Only the assigned HR can reorder/select/move applicants; admins can run AI
  and view. Say if admins should be able to move applicants too.
- Build a proper public "apply" page as a first-class part of the
  product eventually, rather than depending solely on Google Forms —
  more control over validation, file handling, and branding.
- Add basic rate limiting (e.g. slowapi) on auth endpoints before any
  public exposure.
- Consider consolidating error handling on the frontend into a shared
  toast system rather than per-component inline banners, for consistency
  as more flows get added.
