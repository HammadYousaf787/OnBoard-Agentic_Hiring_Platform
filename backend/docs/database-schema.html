Backend Architecture Reference

Employee Onboarding Platform

Database schema, entity relationships, authentication design, and object storage layout for the FastAPI backend powering the admin/HR onboarding and recruitment platform.

DatabasePostgreSQL 18 (onboardingplatformdb)
Object storageMinIO (S3-compatible)
API frameworkFastAPI + SQLAlchemy 2.0 (async)
AuthJWT (access + refresh), bcrypt password hashing

Design note — AI scores live on the applicant row. The four score fields plus overall_score are a strict 1:1 relationship with the applicant and are always read together with it, so they're embedded directly on applicants rather than a separate joined table. They stay NULL until "Run AI ranking" executes for the parent job.
Design note — CV bank entries are snapshots, not references. When a candidate is rejected and saved to the CV bank, their info is copied into cv_bank_entries rather than only linked. This keeps the talent-pool entry meaningful even if the original applicant or job is later deleted — the foreign keys (applicant_id, source_job_id, rejected_by_id) are kept as best-effort links (ON DELETE SET NULL) but the descriptive columns are the source of truth for display.

3.Authentication

Stateless JWT auth with an access/refresh pair, bcrypt-hashed passwords, and an admin approval gate before any new account can log in.

Signup → approval → login

  1. POST /auth/signup creates a user with status = pending.
  2. An admin calls POST /users/{id}/approve (or /reject), which also writes an approval_events row.
  3. POST /auth/login checks the password, then the account status — pending/rejected/removed accounts are refused with a specific reason.
  4. On success, the server issues a signed access token (30 min) and refresh token (7 days).

Token design

  1. JWT, HS256, signed with a server-side secret (JWT_SECRET_KEY).
  2. Payload: sub (user id), role, type (access/refresh), iat, exp.
  3. Every protected route resolves the user via Authorization: Bearer <token> and re-checks status == approved on each request.
  4. POST /auth/refresh exchanges a valid refresh token for a new pair (rotation). Tokens are stateless — there's no server-side revocation list yet.
Passwords are hashed, not encrypted. bcrypt with a per-password random salt is a one-way hash — the plaintext password is never recoverable, even by the platform operators. This is the correct approach for credentials (as opposed to reversible encryption, which would be appropriate for data you need to read back later, like a CV file).

4.Object storage (MinIO)

CV files never touch the Postgres database — they're uploaded straight to a MinIO bucket, and the applicant/CV-bank row only keeps the object key.

Upload path

  1. HR/admin submits a candidate with a CV file (multipart form).
  2. Backend generates a unique key: cvs/<uuid>-<sanitized filename>.
  3. File bytes are streamed to the candidate-cvs bucket via the MinIO SDK.
  4. Only the object key + original filename are saved on the applicants row.

Download path

  1. Client requests GET /applicants/{id}/cv-url.
  2. Backend checks the caller has access to that applicant's job.
  3. A presigned MinIO URL is generated, valid for 15 minutes.
  4. Client downloads directly from MinIO — the file never passes through the API server.

6.What's intentionally out of scope (v0.1)

  1. Not wired to the Next.js frontend yet — the frontend still runs on its own local mock/localStorage data. This backend is a standalone, independently testable API.
  2. No refresh-token revocation/blacklist — logout is client-side only (discard the tokens). A token-blacklist table is the natural next step if that's needed.
  3. No public/unauthenticated "apply to this job" endpoint yet — applicants are currently created by an authenticated admin/HR. A public careers-page flow can be added as its own (rate-limited) endpoint later.
  4. AI ranking is a deterministic mock (hash-based), matching the frontend's simulated scoring — no model is called.
  5. Real "notify me a day prior" delivery (email/push) is not implemented — the flag is stored but nothing sends a reminder yet.
